## Existing authority and proposed reduction

The original notes handler permits owner/admin/project_manager/foreman/field to view, create, edit and complete within their existing company/project scope. PM notes are shared across the assigned project without requiring scheduling, financial or daily-report permissions or an assigned-crew restriction. Field/foreman scope uses the linked team member and the original assignments/workdays/reports projection. No-policy tests discriminate the linked member name from the account label and retain strict numeric assignment-member membership.

The new closed `company.notesRolePolicy` schema is `{version:1,revision:positiveInteger,roles:{admin,project_manager,foreman,field}}`; every role has exactly four booleans: `view`, `create`, `edit`, `complete`. It can only reduce the original ceiling. Mutations require view. Owner is immutable. Unknown roles, unknown keys, assistant/security flags, owner rows, profiles and invalid/missing required policies fail closed for nonowners. Any explicitly present policy—including null, false, zero or an empty string—is required and validated; only an absent property with no durable required/profile marker retains the original defaults. Unknown custom-profile markers require later reconciliation and cannot restore defaults. This schema deliberately does not claim compatibility with PR98's separate shared-file/profile draft.

Fresh effective notes capabilities and revision are assembled before `req.auth` on every atomic request. Required-policy nonowner access through the legacy non-atomic path is refused; no-policy legacy behavior remains unchanged. The atomic wrapper authorizes before counts/history, create replay, edit/deadline/complete changes, mixed changes, no-op and stale revision disclosure. Global Number-aligned canonical numeric project/member/scope identities prevent hidden aliases from altering legacy scope. Note IDs have exact canonical string identity, globally checked against hidden aliases. Historical actor IDs, request identity, text/status/revisions and projected history are validated before delivery. Explicit foreign identity bindings, nested projected IDs and malformed historical state need reconciliation.

The unchanged business handler runs inside the existing buffered tenant candidate. The wrapper validates the complete before/after delta, immutable note bindings, one-row creation/edit and appended history; unrelated company data cannot change. One append-only business audit record accompanies a real direct note change in the same SQL CAS. Reads, idempotent replay, no-op and item-bearing conflict responses recheck current revision, session and account before delivery; writes additionally require the outer CAS. Lost acknowledgement preserves the original request identity and durable replay semantics. A manual create replay retains its existing user/company/project/request identity; this increment does not silently add a session binding to older note saves.

## Assistant and existing UI

Assistant eligibility remains signed-in owner/admin/PM. Field/foreman/crew/platform cannot become eligible through the notes policy. Notes and to-do preview/confirmation/durable replay require fresh view+create; current notes flags and revision participate only in notes proposal authority fingerprints. Scheduling retains its separate grant and project/assigned-crew scope. Ambiguous shared project identity blocks context and every action. Known notes provider drafts suppress generated crew names and fail before provider dispatch/usage reservation when denied; inferred/replayed restricted notes never become ready. AI/chat endpoints remain unavailable in atomic mode. Tests use pure provider mocks only.

The existing notes component consumes the four returned server capabilities, suppresses unauthorized controls and keyboard writes, refreshes on focus/visibility, and clears saved content/history on typed denial. A user's uncertain unsaved attempt/request ID is retained for later explicitly authorized recovery. Legacy responses lacking typed capabilities preserve their original defaults and retry behavior. The existing assistant component blocks denied note/to-do previews and uses the same capability contract. No new settings controls or fake permission checkboxes are added.
