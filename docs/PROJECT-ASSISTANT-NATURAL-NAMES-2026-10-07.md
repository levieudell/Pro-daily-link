# Natural-name first-test regression

Baseline: published main `1eba49a9a9a661563bebe02faf19b9ebd3a7d251`. This isolated draft preserves all published assistant work and billing PR85. No live schedule edits, provider tests, credentials, permissions, merge or deployment are part of this investigation.

## Verified cause and smallest fix

The exact reported input is `Schedule Chloe Andy at market Street tomorrow`. The shipped default Send/Talk path is a deterministic client parser; it does not call an AI model. It required the complete project label, explicit separators/full person labels, and exact dates. Thus it asked for a project even though “market Street” uniquely identified “Market Street Reno,” then could not interpret the possible crew pair or tomorrow.

The bounded fix uses only projects already visible in the authorized workspace and members returned by the selected project's existing authorized context. A unique project fragment of at least two normalized words can choose the context; case, punctuation and standard street abbreviations are normalized. Exact complete labels take priority, including names containing words such as “and.” One-word project fragments, similar projects and duplicate normalized labels receive a short explicit candidate question. Person IDs never select projects; a conflicting project label/ID requires clarification.

Unique exact person/first-name matches can fill a draft. Missing conjunctions between names and near-name spellings receive an explicit confirmation/choice instead of guessing. In the synthetic Chloe/Andi fixture, the owner sentence asks “Did you mean Chloe and Andi?” If both Andy and Andi are authorized, it offers both crew combinations. Duplicate first names show their complete labels. It never ignores an unknown name word or searches an unauthorized member. Unicode letters remain present. Candidate enumeration is bounded; unresolved/overlarge alternatives require a clearer name answer.

The original request remains in memory while project/crew questions are answered, so the date/task/instructions are retained. Yes/yeah can accept only one displayed candidate; it cannot authorize saving. Reserved save/confirm/okay words do not select unrelated entities even if an entity happens to have that label. Guided speech permits yes only for that same one-candidate clarification. Saving still requires the existing exact preview and on-screen Confirm.

## Company-local relative dates and authority

The existing authorized context now includes one scalar `today`, computed by the server's clock in the existing company timezone. Today/tomorrow resolve to calendar dates only after that context is available. Relative corrections fetch fresh authorized context before applying just the corrected date, so a panel left open over midnight cannot use yesterday's cached day. Capture/request generation guards discard late results on Stop, background/blur, close or cancel. The fresh date update preserves previously clarified people/task. For a two-person single-day schedule, changing its date changes both same-day batch endpoints. Contradictory explicit/relative dates and weekday conflicts ask for clarification.

Only actual entity occurrence spans are masked while extracting schedule clauses: a crew member named Tomorrow or Friday cannot supply a date or erase a real date/weekday constraint. Literal Task/Instructions text remains separate. The preview displays the exact actual date and company timezone.

Server authorization, preview validation, signed stale fingerprints, leave/availability, idempotent confirmation and persistence are unchanged. The server module change is limited to the context's company-local date reference. It does not change manual scheduling, estimates, billing, database schema, provider input or the existing notification policy. No new data is sent to AI; the provider request still explicitly whitelists its existing fields.

## Model-based interpretation assessment

The immediate failure does not require model access; scoped matching is smaller and deterministic tests can verify every candidate/authority boundary. This remains a bounded conversational scheduling/notes/to-do workflow. It is not a general conversational AI interpreter. The existing optional Suggest fields action uses server-side OpenAI Responses with the configured OPENAI_MODEL (code fallback gpt-5.4-mini), store:false and maximum 1,200 output tokens. Send/Talk still never invoke it automatically.

If broader structured-intent interpretation is later requested, a separate proposal should restrict one foreground user turn to at most 6,000 characters plus the selected authorized project ID/name, scoped member IDs/names, company timezone and server date reference; exclude customer details, reports, billing, files and secrets. Use the existing provider/model with store:false, no tools, a fixed action/field schema and at most 1,200 output tokens. Proposed additional bounds before any enablement: one request per explicit user turn, no background/retry loop, 20-second timeout, ten requests per user/hour and fifty per company/day, plus an explicit spend cap. These are proposed future limits, not implemented or enabled here. First test with mocks for malformed/injected intent, scope/name/date ambiguity, zero-write previews, stale roles/availability and replay; only a separately approved synthetic provider test could follow. Any model result would still be an untrusted proposal subject to deterministic candidate validation and the existing preview/Confirm server checks.

## Evidence and limits

Pure reducer/name regressions cover the reported sentence, partial/punctuated labels, two Market Street projects, Andy and Andi, unauthorized/unknown candidates, duplicate first names, Unicode, reserved command labels, date/name collisions, explicit-relative conflicts, corrections/Back/cancel and calendar rollover. Actual-handler regressions cover company timezone (including UTC midnight, leap/year rollover), zero-write context/preview, fresh relative correction, stale project/member authority and explicit idempotent confirmation.

Isolated Chromium with synthetic fixtures reproduces the actual shipped-before parser failure, then verifies actual full-app mobile/desktop typed and mocked guided-speech flows, exact-date plain preview, mic-off complete readback, explicit synthetic save, project/crew ambiguity, correction/Back/cancel/reopen and stale confirmation refusal. External routes/providers are blocked; no real microphone permission is granted. Exact-head CI and independent review are recorded in the delivery evidence. Physical-device speech acceptance remains unverified, with the published foreground/stationary limits and typed fallback retained.
