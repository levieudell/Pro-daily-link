## Exact transaction gap

`server.js` currently queues tenants inside one process. `writeDb` replaces the local JSON and starts an unconditional legacy `companies` snapshot upsert **before** its optional `saveTransactionalSnapshot(expectedRevision)` completes. A rejected transactional save therefore does not undo the earlier local/legacy write. Multiple worker disks and outer platform, sales-demo, webhook, bootstrap, migration/account scripts and repair writers do not share one admission point. A policy revocation must increment the same authoritative revision used by the action; otherwise a stale action can overwrite it. The synthetic file lease cannot solve that across hosts.

The existing `database/007_transactional_records.sql` already locks the tenant revision row and checks the expected revision in `replace_tenant_records`, then commits scalar data and records atomically. Policy, account markers, audit and action receipts can use the existing snapshot representation. The assistant CAS ledger writes the private **operations** tenant for spending; it provides no tenant authorization transaction.

## Testable implementation milestones

1. **One tenant repository contract, no production writes.** Introduce `loadConsistentTenant` and `commitTenant(expectedRevision, candidate)` around the existing tenant CAS. REST reads must paginate all records, bracket them with matching revision reads and verify the assembled canonical hash; reject/retry torn or truncated reads within a bound. The existing PG repository can alternatively use a repeatable-read load. Capture no-policy/default fixtures. Synthetic test: change policy between read pages; reader returns a coherent revision or fails closed, never mixed authority.
2. **Commit before local mirror, legacy mirror or response.** In transactional-primary mode stage the entire candidate in memory; CAS is the only authority. Update optional local/legacy mirrors after success, never let them select a newer authority or bootstrap over it. On conflict return 409 with no candidate file, receipt, audit or external side effect written. Synthetic test with two independent workers: revocation wins revision N+1, action admitted at N loses and leaves all stores untouched; reverse order produces one valid earlier action and later revocation. Never automatically retry a user's stale preview under broader fresh authority.
3. **Route every writer through that contract.** Inventory normal routes, session refresh, repair/migration writes, assistant confirmations, guest submission, Stripe `withCompany`, platform/sales-demo/account operations and background scripts. Trusted system writes have explicit service operations, not a permissive user role. Stage notifications/storage/provider work and execute only after valid fresh admission/commit; unsent jobs must recheck current authorization. Reads and long work recheck before protected projection/dispatch. Already delivered/read data cannot be retracted. Test slow request bodies, role/session changes, policy revocation, stale receipts and every bypass writer across independent processes; prove no alternate snapshot can restore revoked access.
4. **Finite workflow registry and scope repairs.** Port PR74's five PM reductions through the unified actor/repository, then implement one audited domain at a time from the table above. Each action defines roles/immutable ceiling, old/new object scope, response projection, compound side effects and supported UI control. Keep financial/pricing, payroll exports, tenant/security/owner/billing/platform and assistant eligibility outside configurable grants. Test role/action reductions, malicious keys, field/foreman identity, cross-company/project IDs and aggregate/file leaks; repair a handler before presenting its checkbox.
5. **Full settings/custom-role flow and exact review.** After registry coverage, replace the standalone PR77 model with server-consumed typed policy/assignments; keep restrictive secondary identities, nonreused profile IDs and owner lockout protection. Require owner reason, per-account impact, signed session/policy/baseline preview, revision/CAS confirmation and audit, and fresh UI invalidation. Unknown/uncovered controls remain unavailable. Run synthetic two-host/real database concurrency tests, independent security review and both exact-head CI workflows before any rollout request.

## Smallest concrete production approval, when code is ready

No SQL migration or privilege expansion is inherently needed for a policy stored in existing tenant scalar data **if** migration007 and its service-role-only RPC already exist for the target tenant. Confirm that read-only during rollout preparation, without assuming the private assistant ledger proves it. The version-bracketed/hash-checked REST loader above also needs no new SQL function.

If the selected tenant is still on legacy snapshots, the first necessary data action is an explicitly named, one-tenant backfill/cutover into the existing transactional tables, from a verified canonical snapshot. A reviewed cutover command must pause/drain every writer for that tenant, compare source and transactional hashes/counts, use expected revision, preserve accounts/grants/sessions, prevent startup snapshot replacement and leave **no role policy installed**. The current `migrate-transactional --apply --company-id` has backup/hash checks but does not itself establish that writer pause or new authority selection, so it must be hardened before requesting approval. No `--all` migration or account/grant change is required for this first cutover.

If migration007 is absent, approve that specific existing tenant revision/record schema and service-role-only CAS RPC installation first; do not broaden anon/authenticated grants. Deployment/activation of the reviewed transaction path is a separate action-time approval. Only after the cutover is verified would an Owner's exact before/after policy preview require a separate approval to change actual production access. Nothing here performs those actions or requests a generic migration/recovery approval now.
