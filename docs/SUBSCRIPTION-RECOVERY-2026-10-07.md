# Standard subscription trial and recovery

Choosing a standard monthly or annual plan during the free trial now sends the original trial end to Stripe Checkout. It does not restart the trial, change the stored deadline, or activate access merely because Checkout opens. Standard prices and plan entitlements are unchanged.

Standard trial Checkout uses the original deadline as `subscription_data.billing_cycle_anchor`, with `proration_behavior=none` and `payment_method_collection=always`. There is no initial charge before the deadline; customers can select their plan and save their card throughout the final 48 hours. The local deadline is never reset or extended. Stripe timestamps have second precision, so the anchor rounds up by less than one second to prevent charging before the original millisecond deadline. Access/trial display still ends at the original local deadline.

Stripe documents this hosted Checkout flow at https://docs.stripe.com/payments/checkout/billing-cycle?payment-ui=stripe-hosted. Completed Checkout can report an active subscription during this initial free period. A provider-verified `original_trial_end` metadata value must match both the subscription anchor and the company's original deadline. Only an Active subscription receives the remaining-trial display; canceled, past_due/unpaid, paused and incomplete status remain authoritative. Estimated gross MRR excludes anchored free periods until their billing anchor. The first charge becomes due at the original deadline; completion after it can collect that period's full payment.

Open same-plan sessions can be reused across the deadline without recreating the subscription. Changed plans expire the old open session and calculate current eligibility afresh. An unresolved creation crossing its anchor fails closed for support recovery, retaining its exact parameters and idempotency key; it never silently switches to immediate payment. Provider failures or near-deadline rejection likewise have no fallback. Such an ambiguity needs recovery, rather than an arbitrary return-at-trial-end restriction for all users.

A canceled standard subscription can start a replacement only after fresh Stripe reads verify ownership, mode, terminal status (`canceled` or `incomplete_expired`), previous completed Checkout and customer subscription history. Any nonterminal subscription, incomplete history, provider error or ownership mismatch fails closed. Customer identity remains; retired subscription IDs prevent late webhook deliveries or old confirmation links from overwriting the replacement. A previously paid returning subscription receives no new trial. Cancellation during this original anchored free period can reuse only the unchanged original deadline, including when local confirmation/webhooks were missed: recovery obtains that proof from fresh verified provider data. Founder recovery requires support review and preserves existing setup/protection terms; exempt/legacy policy is unchanged.

Each tenant's existing request queue serializes create/restore/checkout writes. Failed or concurrent Checkout requests recover the saved attempt, exact parameters and provider idempotency key. A plan change cannot bypass an unresolved creation. Ambiguous legacy creation attempts, expired retry windows or changed price configurations require support review rather than risk a second session. Active project creation and archived-to-active restoration share the same cap; idempotent restoration of an already-active project succeeds. Existing records above the cap are retained, with no retroactive archive or deletion.

## Validation

`node subscription-checkout.test.js` exercises local HTTP signup/checkout/confirmation/webhook/project routes with synthetic tenants and intercepted Stripe traffic. Coverage includes all six standard prices, original/near-end/expired trials, terminal recovery, provider failures and ownership/mode history checks, concurrent retries, late events and confirmation links, active subscription protection, founder support review, and restore/create capacity races. All existing test and syntax commands remain in the package scripts, including assistant/import release checks.

Isolated desktop/mobile Chromium tests verify the trial date/message, selectable canceled plan, retained invoices action, final-window checkout behavior, project restore cap error and mocked replacement navigation. No actual provider acceptance is implied by those tests.

## Deployment and recovery

This is an additive tenant JSON change, with no SQL migration, credential/config changes or mass customer updates. New fields are provider-verified `stripeFreePeriod`, `stripeTrialUsed`, `retiredStripeSubscriptionIds` and durable `pendingCheckout.params/createdAt/livemode`. Earlier paid subscriptions remain protected by fresh provider checks even if the new fields are absent. Pre-repair open Checkouts lacking the preserved trial parameters are expired before replacement; ambiguous pre-repair creation attempts require support.

For containment, set `PDL_CHECKOUT_DISABLED=1`: new Checkout POSTs return503 without provider calls, while existing subscriptions, webhooks, invoices and workspace access continue. No such setting is changed by this draft. Preserve repaired webhook/confirmation guards and the added fields when reverting unrelated UI. A blanket rollback to pre-repair billing code is unsafe: it ignores retired IDs and can resume early-charge behavior. Back up tenant state before rollout; do not delete retired IDs, reset trial dates or cancel provider subscriptions as a rollback step.

Before release, recheck main and review the exact combined head. Keep the current single-process tenant serialization model; this patch does not add distributed locking for horizontally scaled snapshot writers. Actual Stripe sandbox acceptance of anchored no-proration checkout, saved-card collection, initial no-charge behavior, deadline invoice/payment and canceled replacement remains to be exercised separately. Existing screenshots cover the earlier draft and are not evidence of final-window navigation for this revision; the current local HTTP mocks cover it. Prior successful paid sandbox activation remains valid; this draft is not merged or deployed by its author.


## Smallest provider acceptance before release

In an already authorized isolated Stripe sandbox, use a synthetic company with an original deadline a few minutes ahead. Complete one monthly Starter anchored Checkout with a Stripe test card before that deadline. Inspect session payment status/zero initial amount, saved payment method, original anchor, no initial charge, provider-active/local-Trial display and zero estimated MRR. Advance/wait to the deadline and verify the first $99 invoice/payment, webhook delivery, local Active state, entitlements and MRR. Cancel and replace using the same customer: no new trial and one current subscription; replay the retired event to confirm no overwrite. A second annual session should verify the exact $990 recurring price, anchor and no-proration behavior because API behavior can differ by recurring interval. Use test clocks where compatible; no real charges or production mutation is authorized by this draft.

Containment must preserve `stripeFreePeriod` and anchor recognition in webhook/confirmation/access and revenue reporting. Disabling new checkout does not cancel already open Stripe sessions; inspect/recover ambiguous saved attempts and expire unwanted open sessions in the authorized sandbox or deployment process rather than deleting local state. A rollback that drops these fields/handlers can mislabel free subscribers as paid or charge before their original deadline.
