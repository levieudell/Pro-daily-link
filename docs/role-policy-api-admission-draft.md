## Closed workflow

The disabled atomic path admits four owner-only endpoints: `GET /api/company/role-policy`, `POST /api/company/role-policy/preview`, `POST /api/company/role-policy/confirm`, and `GET /api/company/role-policy/audit`. A live Active owner of the selected tenant is required; admin has no policy-management authority in this phase. There is no Roles UI yet. Registry metadata explicitly distinguishes available workflow APIs from the unavailable editor UI.

Preview accepts exactly a request ID, current tenant revision, reason, and complete role rows for the existing six typed families. The32 actions are consumed by their original server modules. Client revisions, unknown flags, owner rows, profile assignments, grants, resources and arbitrary dictionaries are rejected. Existing owner/tenant/security/platform/user administration, billing, pricing and financial/export ceilings remain immutable. The fixed Forged-only signed-in owner/admin/PM assistant gate, separate scheduling grant, project/crew/member scope, features and account locks cannot be policy keys.

An absent family policy stays absent when its requested rows equal the original ceiling defaults. An unchanged valid family keeps its exact policy, revision and required marker. Only a changed or invalid family receives a new typed policy and required marker; only confirmation increments the policy revision. Original individual grants, account roles, project/crew/member bindings, sessions, unrelated settings and business records remain unchanged. Invalid policies can be explicitly repaired within original role ceilings; Active unresolved scope and custom notes profile markers block proposals pending deliberate reconciliation.

The preview shows actual before/after effective account actions, actual notes project visibility, unchanged owner capabilities, changed families, and newly ineligible queued assignment-email IDs/counts without provider payloads. Notes policy activation can remove legacy name/crew-derived field project access even when that role's32 boolean actions stay unchanged; this scope impact is explicitly included. Scheduling family revisions are preserved when unchanged because queued-email admission binds them. Policy requests never trigger generic queued-email dispatch, including retries and workers configured for dispatch.

## Durable authority and recovery

The client preview request ID is a durable originating-session handle. A full source hash, current tenant revision, exact input hash, typed before/after configuration, impact and opaque version bind the review. Preview saves only private proof/audit rows through tenant CAS. Every technical preview advances the tenant revision; another preview, session renewal, role/grant change or business write conservatively makes an earlier unconfirmed review stale. A new request ID and fresh preview are then required. No business policy changes during preview.

Confirmation accepts exactly the original handle/version, its own request ID and `confirmed: true`. Fresh authentication, source/revision checks and recomputed impact precede one CAS containing only changed typed policies, the policy revision, receipt and append-only policy audit. Durable records have closed schemas, tenant/session/actor bindings, reconstructed input/authority hashes, unique identities and linked timestamps. There are no worker-local signing keys or client authority flags. The original audit log and all unrelated roots are frozen by full-candidate validation.

Exact preview retries recover uncertain acknowledgments only while the reviewed source/revision and live originating owner session remain current. Exact confirmation retries recover a committed receipt on another or restarted worker without another save, even after unrelated tenant revisions, while the original live owner session and exact committed policy effect still match. A later policy save, revoked/expired session, role change, changed request input or different confirmation ID denies replay. Known SQL rejection preserves the whole snapshot; unknown SQL outcomes return the existing uncertain-commit error and require exact-input recovery. They never imply the action failed or invite a fresh-ID duplicate save.

All successful non-mutating atomic responses also fence live account/session/revision before delivery. This closes previously buffered scheduling, private leave and time-review read/replay/proposal gaps before policy writes can become available. Mutations retain the existing SQL revision admission point. Already admitted external dispatch claims remain distinct actions; a later policy cannot retract a provider call already admitted by its own claim CAS.

## Guarded SQL source contract and limits

`database/role-policy-commit.sql` is a service-only source contract used by fresh disposable tests. It wraps the existing mandatory-revision replacement RPC and locks the tenant row. It requires the original Active owner, matching live hashed tenant session, matching preview/version/expected revision, and finite non-null deadlines. The earliest session, trial and preview cutoff is checked before replacement and after re-reading owner/session/proof rows following replacement. Any failure rolls back policies, receipt, audit and revision. Missing guarded RPC fails closed; the adapter never falls back to an unguarded writer. PUBLIC, anon and authenticated cannot execute it.

Actual schema application and guarded-RPC availability belong to a separately approved release/cutover packet. This source addition is not an applied production migration. Guarding policy saves does not certify every older business writer's natural-expiry-at-SQL behavior; their existing revision admission and response fences remain, and broader integrated expiry coverage belongs to release review.

At most1000 total preview rows,1000 receipts,2000 policy audit rows and8MB of complete private history are retained. Preview reserves the exact worst-case confirmation receipt/audit space before issuing a review. Capacity fails closed without pruning, erasing committed recovery evidence or rewriting history. Indexed durable retention/compaction is required for sustained release. The per-preview account/project bounds are1000/10000; history larger than these boundaries requires reconciliation.
