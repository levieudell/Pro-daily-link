# Project notes role permissions: isolated integration draft

This branch adds the first complete settings-to-server flow for project notes and to-dos. This reconciliation is based on main `e8c34db3805c1f5544d4fd37fd81c3410c21445b`; it preserves the current assistant pilot, custom work review, labor/date warnings, pay presets, dashboard navigation, signature, filtered-time and saved-timezone fixes. It neither merges the earlier PM-only PR74 nor activates the broad standalone model in PR77. No production settings, accounts, keys or provider data were changed.

## Working flow

In Company settings → Role permissions, the signed-in Account Owner can select **view, create, edit, complete/reopen** for Office/Admin, Project Manager, Foreman and Field. Admin can review the controls/history but cannot edit. The Owner must enter a reason, preview the role settings and each account's before/after profile and permissions, check explicit confirmation and save the exact signed preview. Saving adds one revision and a tenant audit record containing the before/after policy and account impact. Concurrent confirmations of the same revision produce one success and one conflict. Preview signatures bind the tenant policy, user/session, current account roles/status/grants/scopes, reason, payload and five-minute expiration.

Named custom **notes profiles** are optional restrictive overlays on an existing protected baseline. They cannot change account roles, projects, crews or existing workflow grants. A custom profile's permissions intersect its base role's notes permissions. Profiles have immutable base roles and permanently retired IDs; removal clears assignments only through a reviewed policy change. Assigned inactive, demoted or removed accounts are shown for explicit assignment clearing. A durable account marker makes missing policies, orphan/mismatched assignments and base-role changes fail closed.

Private notes routes require a fresh active tenant session even when general demo auth is disabled. View is checked before returning items, counts or history. Create is checked before idempotent replay. Text edits require edit, completion/reopen requires complete, and mixed PATCH requests require both, before no-op or stale-revision disclosure. UI controls use the same typed server result. Role, profile, policy revision and tenant changes invalidate the client context; focus/reload refreshes it, and a denied write refreshes access before continuing. This cannot retract data already read legitimately before revocation.

## Finite allowlist and immutable boundaries

Only the four booleans above and the four baseline roles are accepted by the v1 policy schema. Unknown keys, including assistant, payroll, billing, tenant/security administration and owner controls, are rejected. There is no generic permission dictionary or arbitrary login role. Notes have no approval workflow, so no approval grant is offered. Other workflow controls remain unavailable and retain baseline authorization.

Existing authorization is heterogeneous: Owner/Admin office gates; PM's stored `scheduleCrews`, `viewDailies`, `approveDailies`, `viewTime`, `manageTime` and manager project/crew scope; field/foreman linked-member, crew and assignment/workday/report-derived project scope; separate pricing policy; Owner-only user/billing/export/account lifecycle operations; fixed platform identity. This slice does not broaden or replace those boundaries. Crew remains a membership/team attribute, not an app login role.

Notes scope remains Owner/Admin tenant access, PM assigned project scope and field/foreman linked project scope. With a policy/marker present, field report-derived project authority requires member/labor or linked-workday IDs; report foreman display names no longer grant project authority. Without a policy/marker, the existing defaults remain intact. Policy-on guards also close legacy routes that could manufacture this scope: non-office directory/membership injection, foreign project/crew workdays and reports, report/workday-end foreman identity injection, and direct foreign plans/proposals/T&M summary access. Owner/security protections are not editable. Unexpected loss of a policy while assignment markers remain denies all non-owner notes access and disables policy editing pending repair.

`authenticateRequestAccount(req, db)` freshly projects effective typed `notesPermissions`, `notesPolicyRevision` and `notesCustomRoleId` before assigning general `req.auth`, and private notes/settings use that same authentication helper. This is the shared integration point for the current assistant and manual routes. Assistant eligibility must remain fixed to signed-in PM/Admin/Owner, independent of custom flags; scheduling still requires effective `scheduleCrews` and current project/crew scope. Notes profiles cannot grant assistant eligibility. The assistant now consumes these typed restrictions for note/to-do context, chat, preview, first confirmation and receipt replay. Its AI actor digest and preview fingerprint include the policy revision/profile, and known note provider context suppresses team names. Scheduling remains separately authorized; the fixed company pilot and fixed eligibility remain unchanged.

## Concrete storage choice and limitations

The synthetic integration uses **cooperating processes on one host sharing one canonical database file**. Explicit activation requires `PDL_ROLE_PERMISSIONS_STORAGE=shared-file`, `PDL_REQUIRE_AUTH=1`, Supabase disabled and transactional mode off. All participating processes must use this configuration before the first policy change. Atomic directory creation beside the canonical DB file is the cross-process admission point. Every tenant request loads the newest snapshot after admission and holds the lease through its writes/pending operations/response. POST/PUT/PATCH/DELETE bodies are completely buffered before admission, so a slow upload cannot retain stale authorization while policy revocation commits. Two actual local server processes exercise policy preview on one worker, confirmation on the other, concurrent revision conflict and upload revocation. Assistant previews retain their existing per-worker ephemeral signing key behavior; a first confirmation on another worker safely needs a fresh preview. Assistant note confirmation/body-upload revocation is also covered. Assistant chat/context/interpret fast paths join this admission when it is required; the private operations budget ledger is not tenant admission.

An already-saved local policy/marker also causes an otherwise unsupported local worker with strict auth to join file admission, preventing its ordinary session-refresh writer from overwriting a participating worker's policy. Its notes/settings writes still remain unavailable. Saved-policy workspaces in cloud/transactional/disabled-auth configurations are rejected before remote snapshot selection and legacy tenant route execution. A saved local policy/marker also blocks primary cloud startup replacement. Missing policy and markers preserve original defaults and normal execution when the explicit development mode is absent.

The mode blocks the outer platform, sales-demo and billing-webhook route families, whose writers bypass normal tenant admission. It is a development integration mode and is **not a production deployment configuration**. Independent disks, multiple hosts and cloud snapshot/transactional workers are not supported. The broader cloud rollout needs transactional policy-and-action admission across every tenant mutation path, and a migration/recovery plan. This is a concrete scope boundary, not an assertion that a process-local queue provides distributed revocation.

Leases are never stolen or expired. A request is rejected after five seconds of contention; a hard process crash can leave an orphan directory. Recovery requires stopping all writers, verifying the affected canonical synthetic/local DB path and then removing that one orphan lease directory. There is no automatic stale-lock cleanup that could admit a second live writer. The development preview signing key is shared beside the synthetic DB, created only in this explicit mode, not published, and not printed in test output.

## Validation

`notes-role-permissions.test.js` starts two local processes against an isolated synthetic database and exercises defaults, all four roles/custom restrictions, owner protection, signed preview/reason/expiry/confirmation checks, malicious keys/assignments/baselines, stale owner/session/status/role, missing/corrupt policy and markers, concurrent revisions, denied replay/stale PATCH/mixed PATCH, slow-upload revocation, other-company/project IDOR, scope identity injections, audit/identity preservation, private asset denial and unsupported mode. Existing notes API acceptance and UI fixtures remain in the exact CI suite. Synthetic Chromium desktop/mobile QA covers owner preview/save, PM custom read-only, Admin review-only/edit restriction, field completion restriction, foreman view denial and 390px layout.

Full workflow permissions, notes approval and distributed production admission remain unimplemented. See `role-editor-current-status.md` for the concrete repository/writer/registry milestones and narrowly scoped future cutover approval. This draft is reviewable code and synthetic evidence only; production permission changes require separate action-time approval.
