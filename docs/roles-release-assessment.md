This assessment compares live source main `bdbdfe9a8b038d3dbc32327c58f5a529dbe71225` with the PR118/119 stack. The deployed commit was not verified. There are **10 open technical release gates**, plus **one separate production action-time approval**. The bounded Office/custom/base-role editor for 32 actual actions is implemented. This continuation closes its same-tab page-reload confirmation-recovery prerequisite; it does not close operational workflow recovery or make the whole app ready. Each gate below has a concrete acceptance condition. A route left unavailable cannot count as preservation of a currently used workflow.

## What activation means

Creating an unassigned profile or reading the editor changes no account. An explicitly confirmed profile/base-role change affects only the actual people/actions shown by its preview, within immutable role/grant/feature/resource ceilings.

Activating this stack would also move the selected tenant onto the atomic server boundary. `server.js:atomicRequest` rejects every unclassified `/api/` request with503 **before** its old handler; it does not fall back to legacy authorization. `capability-operations.js` is the exact admitted method/path registry. The scoped workspace replaces raw `/api/state` with finite projections. Consequently, simply switching that tenant to this server would remove the live workflows listed below even with no saved policy. Other tenants and global services must remain on reviewed unchanged routing, while every legacy path for the selected tenant must be fenced. Header routing alone is insufficient.

The draft adds canonical atomic session validation and `capabilityRegistry.actor(db, baselineUser, atomic)` **before** assigning `req.auth`. Actual modules supply fresh `schedulingAccess`, `notesPermissions`, and other typed properties. Stored `permissions` remain existing grants.

`project-assistant.js:allowed` consumes actual `schedulingAccess.create` whenever scheduling policy or profiles are required, existing PM `permissions.scheduleCrews`, current project/crew scope, and fresh notes view/create authority. The fingerprint includes the conditional profile authority epoch; first confirmation/replay and private delivery revalidate current authority. Native cases revoke a profile while stored scheduleCrews stays true and deny the actual Assistant preview; preserved native cases revoke role/grant between preview/first-confirm/replay. The fixed role/pilot boundary stays independent of configurable flags. No conversation behavior is changed here.

This verifies the integrated draft's manual action path, **not** a deployed role policy. An old main host ignores the new policy store. Production must fence that tenant's legacy authenticated/private-read/write/credential/script/provider paths before authority activation. ## Closed next prerequisite: same-tab Roles save recovery

`role-save-recovery.js` is shared by both permission editors. It persists confirmation requestId/previewId/version and the canonical company/account/owner plus **hashed session binding** in sessionStorage before sending, with readback. It stores no bearer/session token, names, policy/profile body, reason, preview payload or checkbox state. Routes/endpoints are derived from a closed allowlist. It never sends on startup, focus or navigation.

A reload only offers an explicit exact-original result check to the same freshly verified owner/company/session. Revocation or definitive private-read denial clears cached private configuration/activity. A known200 stays known even if journal cleanup/readback fails; UI states that limitation, and any later reload still requires an explicit exact receipt check. A rejected retry retains its earlier unknown provenance across reload. Clearing that unresolved record requires explicit current configuration/activity review at the displayed tenant revision; an intervening change requires another review.

The journal holds at most16 unresolved confirmations/32KiB per tab without pruning. Unavailable, corrupt, full or nonpersistent storage blocks a new save before confirmation dispatch. Page reload is covered; closing the tab or ending the browser session is not promised. Uncertain previews are read/review activity only and cannot change permissions; they are not persisted. Operational notes/cards/daily/photo recovery remains G9.

The continuation's exact immutable source review, complete native/browser results and Node20/22 CI links are recorded in PR119 and its checkpoint. Superseded/incomplete runs are not release evidence.
