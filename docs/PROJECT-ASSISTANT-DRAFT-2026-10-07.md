# Optional project assistant — bounded draft

Base: `e949db64e744ebcb509623444c18a7c478e42880` on `main`, freshly verified before implementation. This draft is separate from wall tile, labor audit, pay-period presets, and the Needs report link. It has no production release authority.

## Working first slice

An original orange hard-hat face opens from a bottom-right button on desktop and mobile. It has expressive eyes and a crooked grin, stays static, and opens only when tapped. Native dialog focus, an accessible label, Escape/Close, safe-area spacing, and reduced-motion styling are included.

Signed-in owners/admins and project managers can use it. Eligibility is fixed in UI and server code, independent of any editable role-policy flags. PM project IDs remain the authority; scheduling additionally requires the existing `scheduleCrews` permission and assigned crews. Every action rebuilds the shared request auth actor from the fresh tenant session; the assistant consumes `req.auth.user` permissions rather than client or preview grants. The unmerged role-policy prototype must resolve effective permissions at this shared auth assembly point before integration; no prototype policy interface is presumed live. Notes/to-dos use the PM's existing project-note access without adding scheduling permission. Field, foreman, guest, and platform roles cannot use the assistant API. Existing legacy office accounts retain their existing admin normalization; no permissions are added.

1. Choose an authorized project explicitly.
2. Type a request and follow-up answers, or start optional browser/device dictation. Unsupported or denied dictation offers typing/keyboard microphone. Dictation may use the browser/device's speech provider; the UI explains that before starting.
3. AI suggests editable fields for scheduling, a project note, or a project to-do. The configured server-side OpenAI Responses API receives only the typed request, selected project name, and authorized member names when scheduling needs them; explicit note/to-do requests omit team names. It uses `store:false`, bounded output, strict schema, no tools. No reports, budgets, prices, emails, credentials, customer contacts, photos, or other company/project context are sent. Tests mock the provider and never spend API tokens. Without AI, complete the same fields manually.
4. Choose exactly one authorized person, one future calendar date, same-day 24-hour start/end, task, and daily instructions. Relative dates, implicit hours, duplicate names, and missing fields require a concrete answer/selection. The company timezone must already be valid and must match the preview. This draft cannot configure it. Missing/repeated DST hours are refused.
5. Preview shows the exact project/person/date/hours/timezone/task/instructions and notification policy. Approved leave and overlapping assignments block confirmation. PM conflict messages reveal occupancy without another project's name or private leave reason. Active workdays are protected.
6. Explicitly **Confirm and save these changes**. The existing assignment record builder creates the single assignment and its in-app notification. Daily instructions appear on today's and upcoming My Day cards, and the schedule detail.

For **project notes** and **to-dos**, review exact project/text, existing project-team visibility, and deadline before **Confirm and save these changes**. A note such as “gate locked midnight–6am; can't arrive earlier” is saved literally to the selected project's Notes & To-dos. A to-do such as “pick up the green plastic pieces before anyone leaves today” can explicitly use **Due today**, resolved to the company's exact calendar date/timezone in the preview. No assignee is required or invented; to-dos start open. No completion, notification blast, or public sharing is added. Only existing project-team access controls visibility. Deadlines can also be absent or an explicitly chosen current/future date. The shared notes model/API preserves existing legacy record shapes and supports revisioned deadline history; cards show the deadline. Existing field/crew users can see the note through their current project access while remaining ineligible for the assistant.

**Notification policy:** in-app only. This slice sends no assignment email. The exact preview states this. Manual scheduling keeps its existing email behavior.

## Confirmation and retry safety

Chat/context/preview do not persist or run legacy database repairs. AI calls run outside the company save queue, so provider latency does not block manual screens. All provider text is an untrusted proposal; it cannot execute SQL, tools, background commands, access changes, or mutations.

The preview uses a server-signed, actor/company/project-bound token with a 10-minute expiry and a fingerprint of relevant project/scope state plus member/schedule/leave/workdays for scheduling or project notes for notes/to-dos. Confirmation reauthenticates the active actor and rechecks the relevant tenant/project/member/role/crew/date/time/availability/deadline and fingerprint, then writes the resource and retry receipt together through existing tenant persistence. A due-today preview that crosses the company midnight is refused. Altered tokens/payloads and stale previews are refused. A separate preview from another tab goes stale after the first save.

The persisted receipt binds the exact confirmed token hash and version to actor/company/project and the saved assignment or note/to-do. Concurrent retries and retries after a process restart return the original resource ID without writing or notifying again. Current role/project/crew permission appropriate to the action is still required for replay. Unsaved previews expire when the process signing key rotates. Receipts use existing snapshot/transactional collections and require no migration.

Edit/cancel discards client preview authority. Late responses are ignored after close, actor/company/scope changes, or a newer request. A bounded request timeout releases the panel; an unknown confirmation outcome keeps the original preview locked for the same safe retry. Once a save is known to have succeeded, controls release before the bounded schedule refresh, which checks the captured scope before applying a response. No offline/background save or automatic retry is performed.

## Capability limits and remaining release checks

Scheduling supports only new single-person, single-day assignments with instructions. Project notes and open/unassigned to-dos with no deadline, due-today, or an exact date are also supported. This is not a realtime/hands-free, locked-screen continuous, or PSTN voice system. No screen interaction while driving is required or encouraged. It does not update instructions on an existing assignment, bulk schedule crews/days, schedule overnight work, send email, assign/complete to-dos, answer project-progress questions, create dependencies/cascades, change started/performed work, add subscriptions, or implement trucking/fleet features. Conversation text is held only in the open client session.

Before any separate release decision: exact-head Ubuntu full tests/security/audit must pass; preserve the draft-only status; confirm normal device focus/keyboard and physical supported-device dictation acceptance; inspect current main against concurrent urgent fixes; apply the existing production backup/release process. Provider availability and actual dictation service behavior are intentionally not tested with paid/live calls. No deployment, settings, keys, permissions, or customer record changes are authorized by this draft.
