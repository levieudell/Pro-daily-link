# Bounded photo storage admission draft

This isolated source/test increment is stacked on preserved draft PR107 at `1f0d97eba3e0ab0e5ccd57471db85cd7d9421608`. PR107 and PR103 are unchanged. Atomic mode remains disabled by default. No customer files, production credentials, buckets, settings, grants, migrations, deployment or merge are touched. Local objects and PostgreSQL databases are disposable synthetic fixtures. No shared browser or paid provider is used. The separate urgent business fixes, including PR106 and its unsafe raw rollback candidate, are not imported or treated as live.

## Audited baseline and deliberately bounded contract

The legacy photo writer uploads before database persistence, has project-only file-read guards and does not consistently require PM/foreman whole-crew scope or unambiguous workday bindings. An upload acknowledgement is not a committed tenant reference; cleanup after a commit conflict could erase another worker's winner. Local fallback streams and generic file downloads also lack the required fresh authorization fence. Those original handlers remain unchanged when atomic mode is off.

This draft admits exactly one declared JPG, PNG or WebP image, at most6MB, on an explicit existing in-scope Draft report. The optional workday must have a reciprocal report binding, the same project and entirely permitted participants. Effective typed report/workday actions from PR107 intersect existing role, project and whole-crew eligibility. Field/foreman retain their linked member, own participation or named report authorship and field source. Owner remains protected; crew/platform roles and assistant eligibility cannot be expanded by flags. No new generic permission dictionary or policy-save route is added.

POST `/api/photos/upload-preview` accepts only `{requestId,projectId,reportId,workdayId?,source,phase?,caption?,tags?,file:{type,bytes,sha256,lastModified?}}`. The UUID/request ID must be reused with exactly the same details to recover an interrupted upload. POST `/api/photos` requires `{token,version,confirmed:true,requestId,files:[{type,data,lastModified?}]}` with exactly one canonical data URL matching the preview's size, MIME declaration and SHA256. The unchanged frontend sends legacy bodies and is not yet integrated with this contract; these are source-only APIs.

No pixel decoding, image-format certification, malware scan, EXIF handling or content transformation is implemented. The adapter verifies the declared allowed MIME, provider content type, byte length and SHA256 and serves a fixed image content type with `nosniff`. It preserves original bytes rather than rewriting them. The synthetic positive fixture is a tiny valid PNG; accepting a MIME declaration is not evidence that arbitrary submitted bytes decode as an image. A separately reviewed format-validation requirement must precede any claim of certified image content.

## Durable reservation, commit and recovery

Preview commits only a private upload reservation and audit record through the existing tenant revision CAS; report content, signature, status and all business rows are unchanged. It allocates a server-generated private key under `{companyId}/atomic-photos/{intentId}/photo.ext`, bound to the exact target/details, actor, originating live session, current authority/source, expected revision and ten-minute confirmation version. Plain tokens and image bytes are not saved in the database.

Matching explicit preview retries refresh the token/version/revision while retaining the same reserved key. A refreshed preview invalidates the prior token. Different details or sessions cannot claim an existing request ID. At most200 total reservations, including committed bindings, are accepted. Expired and committed entries are not pruned: their keys are recovery/authorization evidence. Capacity exhaustion fails closed. This cap is a release blocker requiring a separately reviewed durable retention design; it is not a long-term production photo store.

Confirmation authenticates current scope and the source, validates exact bytes, fences immediately before storage, then performs a no-upsert private object PUT and bounded readback. The adapter only inspects the existing `project-photos` bucket policy; it never creates or alters buckets. Public, missing, disallowed or undersized storage fails closed. The provider object is verified before the photo reference, committed binding, receipt and audit are saved in one outer PostgreSQL CAS. Original project-index/report/workday/source/phase/caption/tags/capturedAt/uploader/URL metadata is retained, and the Draft/signature is not modified. New private size/hash/type metadata identifies the exact stored bytes.

No compensation DELETE, garbage collection, overwrite, local fallback, signed/public URL or automatic retry that chooses a new key exists. A conflict, revocation or uncertain commit can leave a reserved object. An already admitted provider transfer cannot be recalled; the final reference is fenced after I/O. That object remains private and inaccessible through admitted reads. Explicit same-request preview/confirmation retry verifies and reuses it. A lost provider acknowledgement can be recovered by exact readback; a lost SQL acknowledgement returns503 and exact committed replay verifies the durable result. Two workers sharing a proof may make multiple PUT attempts; no-upsert/readback protects the single object, one tenant CAS wins and neither deletes the winner. No successful response is delivered before CAS completion.

Exact replay requires identical input, the same currently live originating session, current edit/view eligibility, unchanged authority/source and the unique committed target/key/photo binding. It reads back the stored bytes and fences delivery without adding another reference or upload. Changed or missing provider bytes are never presented as a successful replay. The saved photo can be independently verified through its scoped detail/read endpoint when the original session or source has changed.

## Reads, export and preservation

GET `/api/photos/:id` exposes finite original photo metadata. GET `/api/photos/:id/file` and the exact generated `/api/files/project-photos/{companyId}/atomic-photos/{intentId}/photo.ext` URL expose only uniquely committed references with matching immutable reservation target/details and whole current report/workday scope. They buffer and verify at most6MB, then recheck the authoritative revision, live session and account access before delivering bytes. In-flight revocation conflicts; already delivered bytes cannot be recalled. Missing, changed, wrong-MIME, cross-tenant, ambiguous or aliased references fail closed before success. There is no generic namespace download, stream or Range support.

GET `/api/photos/:id/export` is a separate owner-only attachment download of those verified bytes. GET `/api/photos/recovery-manifest` is an owner-only metadata inventory of reserved and committed keys/descriptors/target IDs. It does not inspect provider presence and cannot certify object existence, reference integrity across every legacy attachment family, or authorize cleanup. It excludes tokens/session hashes. Preserve every reserved and committed key. This inventory is not a complete portable backup or restore bundle. Private reservation/proof records are excluded from customer/public projections.

Unbound project-gallery photos, open workday-only photos, bulk upload, guest photos, plans, company logos, project tickets, estimate attachments, arbitrary/local/legacy file reads, deletes and cleanup remain503 before effects in atomic mode. Their existing original bytes and mappings are not rewritten. Do not activate atomic mode while those required product paths are still unadmitted.

## Evidence and remaining gaps

`photo-admission.test.js` exercises closed input/byte identity, role/report/whole-crew/workday ceilings, duplicate identity rejection, private no-upsert storage, lost provider acknowledgement recovery, changed-object rejection and no delete/provision. `photo-postgres-cases.js` runs inside the existing real PostgreSQL multiworker HTTP suite with a synthetic private object bridge: durable technical-only preview/new-worker confirmation, exact bytes/mappings/signature, scoped and owner export, malicious references/tenant isolation, concurrent CAS winner, mid-upload/read revocation, stale/session/body changes, missing/wrong bytes/type/public policy, rejected and lost provider/SQL outcomes, inaccessible stages and same-key recovery. Earlier scheduling, notes, time, payroll and daily suites remain required; external-provider counters and the foreign tenant must stay unchanged.

The Role editor and server policy-management preview/revision/audit/confirmation route are still absent. No production policy change is made. Remaining writers/effects, UI contract integration, certified image validation, bounded durable reservation/receipt retention, complete attachment backup/restore, existing distributed preview limitations and conflict-safe integration of separate business fixes require independent review and exact integrated-head CI before activation. Production permission, access or storage changes require a separate action-time approved plan.
