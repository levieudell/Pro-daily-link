This isolated increment is based on preserved PR102 (`67c2ab97452c579f2b08359dec9a41fdc0b1e048`). It changes code and synthetic fixtures only. `PDL_TENANT_ATOMIC` stays disabled by default. No production data, migrations, accounts, grants, credentials, settings, cutover, deployment or merge is authorized or performed. Earlier branches and PR102 remain unchanged.

## Audited existing boundaries

Every admitted time/payroll route requires the existing time-card feature. Owner/admin/PM manual create, office correction/removal/submission require existing `manageTime`. PM records require both assigned project and managed crew; manual creation now explicitly checks both in the admission layer. Field and foreman mutation remains their own linked member only. Foreman crew read access never grants crew mutation. Company clock and clock-out remain field/foreman only, with an actual tenant member required.

Period list/summary and time CSV retain existing office time-view eligibility. PM summaries and CSV retain project AND crew scope. Payroll expected-assignment calculations retain the original `managerAssignmentAllowed` EVERY-member crew predicate. Period configuration, capture and fixed JSON/CSV downloads remain owner or admin `manageTime`; PM, field, foreman, crew and platform roles cannot gain them through policy.

`timeWriteRolePolicy` is a closed version1 reduction policy for exactly admin/PM/foreman/field and the finite action list in `time-write-access.js`. It intersects existing eligibility and the earlier time-review view restriction. No owner row, role-management, tenant/security flag, arbitrary permission or assistant eligibility is editable here. Required absent/malformed policy denies nonowner access. With no policy and atomic flag off, the original actor and existing routes remain unchanged. There is no policy-saving route or Company Roles UI yet.

## Finite route admission

`POST /api/time-cards/action-preview` accepts a discriminated action `create`, `correct`, `remove`, `submit`, `companyClock` or `clockOut`, optional exact target ID and closed `details`. `POST /api/pay-periods/action-preview` accepts `createPeriod`, `editPeriod` or `captureExport`. Client-supplied grants, hours, approval, member/project reassignment and arbitrary dictionary keys are rejected. Correction instant values must be explicit valid strings; break objects have finite typed fields. Office break business rules remain the existing permissive office rules; field corrections retain their stricter actual-time/break/lock rules.

Existing corresponding POST/PATCH/DELETE routes accept only `{token, version, confirmed:true, requestId}`. A preview is mandatory; it does not submit, approve, export or alter hours. New admitted GET routes are company activities, report labor suggestions, time CSV, period list/summary and fixed export list/JSON/CSV. Activity creation and every unaudited route still returns503 before effects.

The original legacy handlers compute results in a cloned child admission with a buffered response. Their calculation code is not rewritten. The complete candidate is validated before the outer SQL CAS can stage it. Changes to unrelated cards, unsupported company collections, report fields other than affected-member labor/production labor allocation/history, another person's labor, or mismatched workday/report/project bindings fail closed. Global trimmed duplicate target IDs are rejected before legacy upsert can erase a hidden copy.

An existing office report helper can relink unrelated cards while scanning all tenant time. This was reproduced independently. Such cases now require separate reconciliation and return409 with no preview/business write. The draft deliberately freezes unrelated rows rather than guessing how to repair them. Field correction retains only the existing own single-person active-workday completion and linked DRAFT report labor synchronization, with binding checks. Existing office correction of approved time/report labor remains allowed under `manageTime`, and returns corrected cards to Draft as before; this does not add daily-report approval eligibility.

## Durable previews, confirmation and replay

These NEW previews save a private expiring hashed opaque token/proposal/authority record and a preview audit entry in one tenant CAS. They increment the tenant revision, while making zero business changes. This differs explicitly from PR102's zero-technical-write signed review preview. Generated IDs are provisional; company-clock/clock-out use actual confirmation time. No signing key, key installation or sticky worker routing is needed for these new writer previews.

The response binds the exact action, details, tenant revision, version, actor, effective policy, assigned projects/crews, member link and originating session. Another worker, including one started after preview, can confirm from the durable proof. Every preview invalidates older pending previews through the company revision. At most200 unexpired previews are retained; expiry is10minutes and expired previews are pruned on the next preview. This conservative global contention is a known usability limit.

Confirmation freshly authenticates after receiving the entire body, checks the current proof/authority/feature/scope/business state, reruns legacy rules, and atomically commits business changes plus receipt and audit. A concurrent role/session/policy/card/workday/export change wins through the SQL expected-revision check; no partial change or successful response escapes. Exact replay across workers/restarts requires the originating live session, identical request and unchanged authority plus relevant business collections. Lost acknowledgement returns503; identical receipt replay can then verify the committed result. A different session/request/action/version cannot reuse the proof. Private proofs and receipts are excluded from broad customer export/state paths.

New read responses are buffered, projected to finite fields and fenced against a fresh authoritative revision before bytes/CSV headers are sent. Revocation during generation returns a conflict response; failed generation/persistence cannot return successful export bytes. The read fence establishes a current snapshot check, not a guarantee to recall bytes already delivered before a later revocation.

PR102 leave/card approve/unapprove previews and the inherited assistant preview still have their documented worker-local first-confirmation/restart constraint. This increment does not fix or claim production readiness for those older paths. Their durable receipt replay remains available. Overall atomic runtime remains a disabled, partial admission draft.

## Business rules preserved

The original gross elapsed-time quarter rounding happens FIRST, followed by subtraction of unpaid meal durations, then quarter rounding/clamp. Paid rests do not subtract. For example1h08m gross minus7m unpaid meal still produces1.25h. Clock-out keeps its existing gross-quarter computation. Field PATCH requires its original raw-row revision; approval/status alias, closed/exported period, active/shared-workday, overlap, future actual end and break locks are unchanged. No automatic submission or approval is introduced.

Pay-period inclusive ranges, overlap guards, saved timezone, whole overnight clock-in-day assignment, readiness counters, missing scheduled entries, approved-hours summary and source hash remain the original `pay-periods.js` implementation. Capture requires readiness, latest export ID and correction reason where applicable. Existing v1 JSON/CSV remains immutable when v2 is captured. There is no new payroll formula, pay rate, billing, payment execution or eligibility.
