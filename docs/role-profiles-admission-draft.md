# Office and restrictive named role profiles — isolated source draft

This increment is stacked on the frozen operational Roles draft (PR118, `e793b482aa2babecf2908366184aff76adfc74b8`). It supplies a genuine Office definition, optional custom named profiles, explicit account assignments and an owner editor for the existing 32 server-enforced actions. It does not seed profiles, infer assignments, rewrite roles or activate atomic mode. Production grants, accounts, sessions, credentials, SQL and deployment remain untouched.

## Model and scope

`company.roleProfilesRequired: true` and `company.roleProfiles` form a closed versioned model containing revision, definitions, explicit assignments and retired custom IDs. Each definition has a permanent ID, name, kind, immutable existing base role, profile revision, exactly six typed capability families and the literal scope inheritance `existing-role-and-assignments`. Limits are 50 definitions, 1000 assignments and 1000 retired custom IDs. Unsupported keys and action names are rejected. Names are distinct after Unicode normalization and case folding; protected role/security/billing names cannot be impersonated.

Office has its own protected ID, kind, name and editable capability definition. It starts unassigned with an explicit eight-action read allowlist: scoped scheduling, time off, time review, pay periods, activities, dailies, workdays and notes. It inherits the existing Admin base; legacy stored `office` accounts remain byte-for-byte unchanged and can be explicitly assigned it. This phase cannot convert a Field/Foreman/PM account into Office/Admin or introduce a new authority-bearing base role. Office therefore retains the existing Admin company-wide resource scope and fixed financial/Assistant eligibility. Those inherited boundaries are stated in the editor and are not inferred from the profile name.

Custom profiles inherit one existing Admin, PM, Foreman or Field base. Their action masks can only intersect actual base-role policies, stored grants, feature locks and original resource scope. PM projects and crews, Field/Foreman linked member and project scope, customer privacy and team visibility remain unchanged. A Crew remains a membership attribute. Named profiles never grant account/tenant/security/platform/billing administration, pricing, public sharing, provider access or Assistant eligibility. Signed-in PM/Admin/Owner eligibility remains fixed; scheduling additionally consumes the fresh typed scheduling restriction and existing grants/project/crew checks.

Creating a profile does not implicitly activate a base-role policy or tighten its scope defaults. In particular, original shared-project notes visibility remains exact when no ordinary notes policy exists. The preview compares the real current and proposed project visibility; any later activation of a base notes policy is a separate reviewed change.

Malformed, missing required, duplicate, foreign or protected-target profile state denies all nonowner typed actions; finite errors withhold private configuration. A legitimate assigned account whose base role no longer matches receives a restrictive mismatch descriptor. Ordinary account-role edits require explicit reviewed profile removal first. Owner action access bypasses restrictive profile corruption; the profile manager returns reconciliation-required rather than guessing or silently repairing damaged data.

## Owner workflow and transactions

Company settings exposes a separate Office/custom profile editor beside the base-role matrix. Only the current owner can read definitions/eligible account choices, preview or confirm. Admin management remains unavailable. Creation, definition edits, matching-base assignment/removal and unused custom retirement are distinct closed operations. Office identity/base/scope cannot be changed or retired. In-use profiles cannot be deleted: every assignment must first be explicitly reviewed and removed/reassigned. Retired custom IDs cannot be reused.

Each change requires a reason, current tenant/model/profile revision, a durable preview of actual affected people/action differences/scope visibility and an unchecked explicit confirmation. Assignment/name/revision changes count as affected people even without an effective action difference. The existing owner policy API retains preview/proof/receipt/audit shapes and the same SQL policy guard/CAS; there is no new generic grant dictionary, SQL schema or second authorization store. Original six-family history and absent-policy hashes stay compatible. Profile configuration is included in new proof/effect hashes, delivery checks and business action authority.

UI generations and current identity/revision fences make late responses inert after navigation, session change or tenant switch. Blur/focus/expiry clear confirmation. Unknown results retain the original request under the original page identity and support explicit exact-ID recovery through route close/reopen. A known successful save survives failed read-only refresh without another write. Both permission editors now preserve only original confirmation IDs/version and company/account/owner plus hashed session binding across same-tab page reload, with no automatic request. Uncertain previews are not persisted. Storage failure blocks a new confirmation before dispatch. A rejected exact retry preserves unknown provenance until explicit current-revision activity/configuration review; denied access clears private cached state. Tab closure/browser shutdown and operational action recovery are not claimed. See `roles-release-assessment.md`.

History remains bounded by the existing 1000 preview/1000 receipt/2000 audit rows and 8MB aggregate reservation. Full profile before/after snapshots participate in the capacity calculation; no pruning or recovery-record deletion is introduced. Sustained use still requires indexed retention/compaction preserving committed authority, live proofs and uncertain recovery evidence.

## Validation and release limits

Tracked pure tests cover exact unassigned defaults, all six real dependent action modules, immutable base/grants/scope/Assistant/owner boundaries, actual affected accounts, closed malicious shapes, mismatch/in-use/retirement, stale/revoked/expired confirmation, legacy proof compatibility and the supported 1000-account/50-profile directory. Evidence reuse is confined to a synchronous read-only evaluation: later requests/candidate mutations revalidate the model and no cache crosses an await.

The tracked synthetic PostgreSQL HTTP cases and private browser cases run without a suite filter alongside the complete prior native stack and its 30 browser journeys. They exercise actual accounts/workflows, two-worker CAS, rejected and lost acknowledgments, restart recovery, exact receipts, slow/inflight revocation, malformed stores and tenant isolation. Local native PostgreSQL/browser evidence, immutable-head independent review and exact Node20/22/PostgreSQL CI are recorded in the final PR/checkpoint; incomplete runs are not credited as passes.

The bounded R5 profile model/editor is a source prerequisite for the admitted 32 actions. Broader R3 domain actions, distributed first-confirmation work outside the admitted stack, indexed retention, remaining operational browser restart recovery and the R6 integrated production rollback/migration/cutover/private-read/write/provider packet remain separate release blockers. No migration or production activation is requested or performed here. Any actual production permission change requires separate action-time approval.
