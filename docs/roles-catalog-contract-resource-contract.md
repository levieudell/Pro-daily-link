# Catalog and project contract resource adapters

This local draft adds four existing writers to the reviewed resource workflow. It does not introduce role-policy flags, change production access, or enable a deployment. Source baseline: `ac1e3bc812cc8ecec3a8d1f060f33a069f2f5877`.

| Operation | Existing route | Fixed baseline | Exact effect |
| --- | --- | --- | --- |
| `catalogCreate` | `POST /api/catalog` | Active Owner, Admin or PM | Append one server-ID catalog item, including server timestamp. |
| `catalogApply` | `POST /api/catalog/:id/apply` | Active Owner, Admin or PM; PM current project scope | Append one estimate item to the selected current project, deriving item name/unit, zero cost and rounded labor budget from the current catalog item. |
| `projectContract` | `PATCH /api/projects/:id` | Active Owner or Admin; existing pricing access and contract tracking enabled | Change only contract value and its formatted budget. |
| `projectContract` | `PUT /api/projects/:id` | Same as PATCH | Same as PATCH. |

The catalog already has an Office-role baseline without a pricing requirement. This adapter preserves it. PM catalog application now requires the existing `canAccessProject(db, user, projectId)` helper; the original handler omitted its destination-project check. Contract PATCH already checks contract tracking. The adapter applies that same gate to PUT, preventing the existing PUT bypass. These explicit corrections apply to the selected resource workflow; the legacy handlers remain untouched in this slice.

Inputs are closed and bounded. Catalog creation accepts only name, category, unit, target hours per unit and description, with the existing General/zero/empty defaults. Catalog application accepts only a positive current project ID and positive finite quantity. Contract changes accept only a finite non-negative numeric contract value. The adapters reject string-number coercion, arbitrary pricing or security fields, unsafe IDs and excessive derived labor budgets.

Delta validation compares complete affected collections and all other top-level collections. It accepts the existing handler's exact append/contract effects and rejects reordered or duplicated project targets, old estimate edits, historical rate changes, changes to accounts, and other extra mutations. The receipt privately retains the previous complete project for estimate application and contract changes. Catalog creation requires no previous record removal. Server-generated IDs and timestamps cannot be supplied by clients.

Readback projects current authorized records only. It never returns retained project history or cached historical receipt content. PM readback rechecks current destination scope and suppresses cost when existing pricing access is denied; preview does likewise. A missing, re-bound or removed original row yields a technical ID/receipt acknowledgement. Catalog creation checks the original server timestamp before identifying a current row with a reused ID. Contract readback returns a technical acknowledgement when tracking or pricing access is no longer present. Shared admission still handles actor/session/revision binding, preview expiration, guarded CAS, confirmation, receipt proof, unknown-result lookup and role revocation.

Integration uses these six exports from `resource-catalog-contract.js`: `route`, `parse`, `authorizeActor`, `authorize`, `validate` and `currentResult`. Pass the existing resource-input helper object and existing `canAccessProject`/`canViewPricing` helpers. Both contract methods use the same operation kind. The fresh main's project-date PATCH shares this route; the root dispatcher must match the explicitly named operation kind and reject mixed contract/date payloads. Catalog application must preserve the original 201 response status, including replay.

`resource-catalog-contract.test.js` covers closed schemas, fixed roles, inactive actors, current PM scope, missing scope helper, pricing/tracking gates, malformed source IDs, excessive derived values, exact deltas, retained histories and fresh finite readback. Its synthetic HTTP section runs the actual named handlers through shared admission using its own memory repository, its own localhost server, five synthetic actors and empty provider credentials. It checks all four writer signatures, raw-write rejection, preview without business mutation, foreign/missing records, confirmation after scope revocation, idempotent replay, durable lost-acknowledgement lookup without resend, new-session lookup denial, cross-tenant requests and unchanged legacy-file bytes.

The slice's real HTTP verification requires root integration into `resource-inputs.js`, `resource-deltas.js`, `resource-admission.js` and the resource helper set in `compat-workspace.js`. The isolated slice uses uncommitted finite family wiring in those four files solely to execute this verification. Only this adapter, its test and this contract document are deliverables. Native PostgreSQL, normal browser forms, broader release checks and independent integration review remain the parent task's responsibility; this slice makes no claim that those checks passed.
