# Daily report, workday and reporting export admission draft

This isolated source and synthetic-test increment is based on preserved draft PR103, `5d6eb6e66e1e348cd716d3360bbf14aa37851a6e`. Atomic runtime remains disabled by default. No production access, accounts, grants, settings, credentials, migrations, data changes, merge, cutover or deployment are performed. Earlier worktrees and PR103 remain unchanged. The separate main-based assignment-to-daily and duplicate schedule-hours fixes are not edited or imported here; integration must preserve those fixes and repeat validation after resolving any server conflicts.

## Audited existing behavior

The original report creation route accepts an arbitrary extracted dictionary and an invalid explicit project ID can fall back to a client project index. Creation also calls whole-company preparation which can merge matching Draft reports, alter narrative, relink cards or purge unrelated records. Those behaviors cannot safely become an unrestricted policy writer. This draft accepts an explicit project ID and closed report fields, then rejects the complete candidate if it replaces an existing Draft or changes unrelated business records. Reconciliation is a separate task; no automatic deduplication, historical cleanup or production repair is added.

The original PM guards sometimes accept any managed crew member, and workday close lacks a project/crew guard. The new admitted actions require current assigned project and every source and destination crew member. Field and foreman require a valid linked member, current project eligibility, same current crew and their own participation or existing named report authorship. An approved report correction additionally requires office approval eligibility. Unsupported crew/platform roles cannot gain access from grants or custom flags.

Original report PATCH changes report labor/production and history without syncing linked workdays or cards; this remains unchanged. Workday end creates only a Draft with an empty signature and no accepted production entries. It computes report labor at hundredth-hour elapsed rounding, closes existing open cards at gross quarter-hour rounding, keeps cards Draft and uses the original workday/report date rules. For a synthetic 68-minute workday the report shows 1.13 hours per participant and cards show 1.25 hours. No automatic submission or approval, new allocation formula, meal rule or historical recalculation is introduced.

Submission still enforces existing allocation, template signature and photo requirements. Explicit office approval retains missing-data, multi-line allocation and unresolved flag checks, signature/history, project progress and first-approval captured T&M/hybrid rates or historical rate-review markers. Financial fields are freshly projected according to the existing company pricingAccess setting; field/foreman and a nonpricing PM cannot receive them. Pricing setting changes invalidate confirmation and priced receipt replay.

## Finite routes and closed policy

POST `/api/daily-actions/preview` accepts `{action,id?,details}` for only `createReport`, `editReport`, `approveReport`, `startWorkday`, `endWorkday` and `captureExport`. The corresponding original report create/PATCH/approve, workday start/end and reporting-export create routes accept only `{token,version,confirmed:true,requestId}`. Arbitrary grants, extracted metadata, fallback project indexes and unsupported nested fields are rejected. The internal candidate marker is server context only, and method/path/details are reconstructed from the finite action definition.

GET report and workday collection/detail routes return finite fields, require the effective view action and filter by entire current project/crew scope. Optional projectId filtering can only reduce that scope. Reporting-export capture, list, fixed JSON and CSV remain owner-only, including when admin, PM or field policy grants are supplied. Payroll, billing, role management, tenant/security administration, owner access and assistant eligibility are not configurable through this module. Assistant eligibility remains the independently fixed owner/admin/PM rule and existing scheduling/project-note restrictions.

`dailyRolePolicy` is a version1 reduction policy for exactly admin, project_manager, foreman and field, with positive revision and exactly six typed booleans: viewReports, createReports, editReports, approveReports, viewWorkdays and runWorkdays. It intersects existing eligibility; it never broadens the role floor. Approve requires view and remains office-only; run requires both workday view and report creation. With time cards enabled, run also intersects the existing typed time-writer capability: own clockCards for field/foreman or office createCards plus correctCards and existing manageTime. Required absent/malformed policy denies every nonowner action. Owner has no editable policy row. With no policy and atomic mode off, the original actor and production route behavior remain unchanged.

No Company Roles UI, policy-save endpoint, permission grants or live policy are shipped here. The unchanged frontend sends legacy bodies and cannot use these source-only admitted APIs yet. Its richer production rows include fields outside this bounded request/projection, such as catalogItemId, workDescription and pending/unplanned markers. A separately reviewed UI increment must translate closed fields and show validation, preview and explicit confirmation before any activation.

## Complete candidate and durable confirmation

Original handlers execute in a cloned child snapshot with a buffered response, no finished child transaction and no pending external effects. The admission validates the complete candidate before the outer PostgreSQL expected-revision commit. It freezes unrelated reports, workdays, cards, project settings and prior audit entries. Approval may alter only the target project's existing progress/production counters. Report edits cannot silently relink cards or alter workdays. Duplicate trimmed target identities and ambiguous project/member bindings require reconciliation.

Workday close checks every linked card, including hidden/deleted records, before the original close helper runs. Foreign project/member cards, missing crew cards while the feature is enabled, duplicate open cards for one participant, invalid start instants and open-card approval/status aliases or payroll/export/period locks reject the whole candidate. A legacy workday started with time cards off then closed after the feature is enabled requires separate reconciliation. Closed card history and bindings are preserved. The new layer does not repair source rows or reconcile elapsed report hours with differently rounded cards.

Preview saves only a private hashed opaque token/proposal/authority record and audit event in one tenant CAS. It changes the technical revision but no business record, hours, signature, status, export or storage byte. Proofs bind the exact action/details, expected revision, version, actor, current typed policies, pricing policy, project/crew/member scopes and originating live session. IDs in preview are provisional and workday clocks use actual confirmation time. Proof expiry is ten minutes and at most200 unexpired proofs are retained. Each preview bumps the global tenant revision and invalidates older pending previews; this conservative contention is a known usability limit.

First confirmation can run on another worker or a worker started after preview. It authenticates after reading the complete body, checks the durable proof and current scope/authority/revision, reruns original business rules and commits business changes plus receipt/audit atomically. Lost acknowledgement returns503; exact durable receipt replay across workers verifies the committed result without another change. Replay requires the same live originating session, identical input and unchanged authority and relevant business collections. Completed workday replay rechecks scope and the saved effect rather than reopening the day. Changed policy, role, crew/project, pricing, source, session or request rejects replay/confirmation. Proofs and receipts are excluded from general customer export/public snapshots.

Reads, cached results and CSV bytes are buffered and checked against a fresh authoritative revision and session/account access before response delivery. An in-flight revocation returns conflict; bytes already delivered before a later revocation cannot be recalled. First-confirmation durability here does not remove the inherited worker-local preview constraints of older review/assistant paths.

## Fixed reporting exports and unsupported effects

Owner captures retain the existing approved-only inclusive date range, explicit ISO-date requirement, captured rates, financial completeness/null semantics, signature and approval history, version/supersedes/reason checks, original snapshot hash and existing CSV calculation/escaping. JSON exposes finite known project, estimate, rate, report, team and total fields; arbitrary nested metadata is excluded. The stored snapshotSha256 remains the original captured raw snapshot digest, not a digest recalculated from the projected JSON or PostgreSQL jsonb key order. Later report/project changes and new versions cannot rewrite v1 JSON/CSV or history. Historical missing-rate exports remain explicitly incomplete with null laborAmount and group amounts.

Photo/upload/storage writes, file downloads, guest/public sharing, report delete/safety/disposition/rate-review, state, action-center, exceptions, broad production/insight aggregates and every unaudited route remain503 before effects. Existing photo upload saves bytes before database commit and has no safe compensation/outbox; this draft does not claim to solve full photo persistence or recovery. It tests interruption by rejecting upload after a persisted Draft, preserving its identity/content for an explicit PATCH retry. Configured photo/signature requirements still prevent submission until trusted synthetic fixture metadata supplies the required photo; no real bytes or provider calls are used.
