This isolated draft extends PR134's source-only account adapter. The initial main baseline is `bdbdfe9a8b038d3dbc32327c58f5a529dbe71225`; main advanced independently through UX PR136 to `8356690a62e5b7806399c8ba64d85d28882ac7ec` during review. Ordinary startup cannot install this feature: the explicit installation hook requires test mode, strict authentication, a synthetic marker, canonical selected company, loopback origins and synthetic local storage. ## Complete account slice

The existing login/setup, forgot/reset, verification link/resend, owner profile, account directory/add/edit/reset and employee-with-login forms use the consistent selected-tenant snapshot. The public global signup/founder service and other tenants keep legacy persistence. Existing global links redirect to the configured selected origin; no-hint global company lookup delegates only a bounded email lookup to current selected authority, then redirects before transmitting login credentials. A shared selected/legacy email fails closed until an explicit company link is supplied, including remembered-company reset entry; unavailable/non-OK configuration remains unknown and requires safe current discovery rather than trusting a remembered tenant; empty current discovery submits no mutation and malformed discovery fails closed, while successfully known ordinary configuration retains the original path; explicit selected and foreign links retain their respective authority, foreign links opened on the selected origin redirect to their configured legacy service before credentials and never replace tenant intent, and no-hint credential mutations on the fenced global service are denied. A bounded cloud catalog cannot prove a globally unique email, so cloud-backed selected discovery requires an explicit company link; no unverified provider/capacity assumption can choose the tenant. Ordinary fence-absent discovery retains its original selection rule. No credentials, cookies or provider secrets are forwarded between those services.

Setup lasts72 hours and retains the existing server minimum10/UI minimum12. Reset lasts30 minutes/minimum12 and revokes the affected user's sessions. Verification lasts24 hours and preserves sessions. Valid legacy credentials without a new generation ledger remain accepted; present malformed markers are denied. Owner/user-cap/unique-email/member/project/crew/default-grant rules are retained. Office remains the existing Admin alias; Crew remains a member attribute. Account identity, grants, management, time access, security, billing and ownership do not become editable policy flags. Assigned profile/base-role changes require the reviewed profile removal before a role change. Field and platform accounts cannot become Assistant-eligible through these operations.

Owner security changes require an actual server preview with before/after impact, reason, current revision, expiry and an unchecked explicit confirmation. Its finite impact also names counts of revoked manual password recovery, reset/verification links and queued/admitted deliveries; queued sends are cancelled and admitted sends retain uncertain provenance. These reviewed credential revocations are additional conservative effects, including on time-access or name-only edits. Existing setup codes retain their legacy validity unless replaced or the email changes. The finite method/path schema covers account create/edit, linked-member create, temporary-password replacement and protected time access. Preferences retain their current owner-only prefix authority. Unknown input keys, arbitrary grants, ownership transfer and cross-company/project/member IDs are denied. The actor is freshly assembled from current account/session and the reviewed six typed controllers before `req.auth`; login/me expose the actual32-action family restrictions in addition to the unchanged stored individual grant fields. This slice does not certify other handlers against those policies.

## Private recovery and delivery

HMAC proofs bind the entire closed preview/receipt descriptor, including owner, originating session, company, operation/input/impact, reason, revision and expiry. Exact confirmation replay retains its original preview and review revision. Manual eight-character temporary passwords use a separate versioned AES-GCM envelope bound to that owner/session/operation/target/current generation and effective authority. Only the fresh originating owner session can obtain the named secret after acknowledged CAS; stale or buffered results are suppressed. A different key or version fails closed. Two workers/restart reuse the same purpose-separated synthetic key bundle; there is no automatic live key rotation or credential provider setup in this draft.

An interrupted confirmation is checked through the original operation, never automatically resent. The browser stores only company/session binding and operation ID, reads that identity back before first confirmation, and checks current server identity before rendering private responses. Known confirmation or reconciliation stays successful even if browser cleanup fails. Only when the synthetic lifecycle review is active, confirmed account creation renders the named temporary password before its optional directory refresh; refresh503/network failures retain that delivered result and report the known saved outcome. A confirmed edit applies its safe result before refresh and reports its acknowledged save. Ordinary flag-off handlers retain their original readback/render ordering. Access-change denial clears the password and reports the known save plus required sign-in, rather than claiming a password remains shown. Definitive session/account/owner denial clears private review/result DOM, the finite account-directory and personal-display/preferences caches and cached management authority; local account/profile rendering and reopening remain blocked until a fresh bootstrap while retaining original operation provenance. The finite directory and preferences readbacks are checked before legacy consumers render private data or a dependent temporary password. Consumed/expired/changed results have an explicit current-account reconciliation with revision/reason/confirmation and retained original server history; an absent current receipt is not described as an unsaved action.

Reset and verification use purpose-specific encrypted bearer custody committed before guarded send admission. Admission and final receipt attachment recheck current account/generation/email/expiry. Unknown delivery is retained without automatic resend or lease takeover. Rotation/revocation archives safe terminal or uncertain provenance and removes obsolete ciphertext, preventing past terminal deliveries from exhausting the old500-entry queue. History is append-only. Broader indexed retention, archival performance and live key lifecycle remain G9/G10 release work.

The optional test-only global cohort file fences selected snapshots before local writes, primary cloud hydration, no-hint primary selection and null-fresh-snapshot fallback, discovery/session search, platform owner reset/support grants/pre-existing support sessions, both legacy cloud adapters, their exported raw core-table requests, direct transactional repository and verified backup. Minimal successful legacy writes remain successful. The selected native adapter uses the explicit revision CAS, and session/proof/trial deadline is checked after SQL row-lock acquisition and again after replacement before COMMIT.

Account pages may load with expired retained ticket sources. In this test installation, physical file retention is deferred without claiming purge or changing historic source/audit rows. Implementing that retention job belongs to G6/G9.
