# Managed Company Roles recovery copies

This successor advances the existing draft PR #190 from reviewed 75d749d. It adds a managed-compatible writer without executing SQL or activating a tenant, changing grants, provisioning buckets, changing editable role permissions, or restoring business data. The reviewed 75 source and its installation packet remain separate immutable evidence.

## Captured scope and integrity

Only explicitly configured Company Roles tenant UUIDs are eligible. Current authentication mode, signing key, cohort membership, transactional mode, native managed source and company binding are checked during I/O. The platform envelope and separate Assistant ledger are excluded. A known successful Roles commit queues a background check; startup reconciles cloud copies and an hourly timer observes the existing daily cadence. Nothing writes backup state into the company snapshot or Roles provider-attempt ledger.

Format caps do not bound peak process memory: the initial snapshot clone, serialization and encoded chunks can coexist. The named tenant must pass a memory/egress sizing review for the actual service before activation. Existing admitted jobs are checked before reading physical attachments; incomplete originals remain read-only reconciliation cases. No paid-provider sizing or production trial was run for this draft.

Each recovery set identifies one atomic repository snapshot and authoritative `roles_revision`. It is a **historical capture**, never a claim that it matches the current/latest revision. Capture time is pinned before the source read; sealing and verification have separate timestamps. Canonical snapshot hash and serialized-byte SHA256 are different recorded checks. A concurrent later revision does not change the captured snapshot. Same-revision content drift, regressed revision, lost managed authority, missing storage or incomplete evidence fails closed.

The closed attachment inventory covers company logo, photos, project plans, retained project tickets, estimate imports, and project proposal source PDFs. Both current storage aliases and canonical protected URL references are recognized. Cross-company keys, contradictory aliases, traversal/encoded paths, remote URLs and unbound local URLs refuse completeness. A purged ticket with no retained reference remains in the snapshot but has no attachment to copy. Deleted tickets whose references remain are included.

Normal files are read from the original tenant-owned object and their bytes are checked again before seal. The manifest records attachment **read-time** hashes; older physical references do not contain an original upload hash, so this is not a point-in-time storage transaction. Immutable application upload keys plus the stability check establish the supported recovery copy. Signed compatibility uploads are copied from private inline custody: their asset MAC, complete resource receipt/preview MAC and original reference binding must validate. Removed historical references and orphan provider files are not certified. Inline orphan custody still remains in the captured snapshot.

The existing private `tenant-backups` bucket must already admit JSON at the required size. It is never created or modified. Raw chunks of 6,000,000bytes are encoded into bounded JSON objects of at most 8,100,000bytes; snapshots are bounded at 160,000,000raw bytes, individual referenced assets at 15,000,000bytes, and the complete snapshot plus copied assets at 256,000,000raw bytes. Limits are 2,048unique objects, 10,000reference bindings, 4,000,000bytes per signed metadata document, and fewer than 3,200 admitted job directories. Capacity failures require operator review; there is no automatic deletion or pruning. These limits do not promise that every existing tenant fits.

## Original job and recovery handling

Migration 011 adds a server-only immutable admission ledger with no direct browser/service-role table grants. Three narrowly scoped service-role RPCs read, list, or admit a named managed tenant job; private helpers, forced RLS, guard/ACL contracts and deferred admission deadlines fail closed. Native row locking and a unique company/job key commit the signed original descriptor before any backup storage dispatch. An unknown admission ACK is reconciled by reading that original row. A deterministic company/day/revision/serialized-hash directory then receives the same signed original descriptor, unique writer nonce, numbered chunks and final signed manifest. All object writes use no-upsert POST, followed by exact-byte readback. Purpose-separated HMAC uses the existing backend key; signing identity is recorded. Unknown acknowledgements are reconciled by reading the original object only. Another worker or restart cannot take over or resend an incomplete original job, switch its destination, or infer success from a timeout. A later source revision or day is a distinct capture and does not resolve the earlier unknown job.

Each operation has a five-minute overall deadline and thirty-second bounded I/O waits. Late sealing cannot refresh an old snapshot. A timed-out write may still reach storage, so its original identity is retained and only read-only reconciliation can establish its outcome. Signed metadata rejects unknown fields, path aliases, foreign company bases, altered manifest/core bindings, missing/extra references, noncanonical base64, chunk/whole-file hash mismatch, future times, wrong key or capacity overflow.

Startup discovers immutable admitted originals from the named tenant ledger, orders valid captures by source revision and capture time, then validates the complete snapshot and every copied attachment. An incomplete or corrupt candidate establishes no proof. A valid older historical set can still be reported with its explicit source revision and age. A private signed local receipt is only an integrity-verification cache; it does not replace the original manifest. Current configuration/key/cohort drift suppresses its verified/fresh status while preserving the original receipt. Cloud manifests support reconciliation after local disk loss; they do not supply a mutable cross-worker latest pointer.

Health preserves the existing 540c64e legacy receipt contract for unmanaged tenants. Managed status reports its captured revision, age and integrity separately. `independentCopy` and `restore` remain `not-checked`: this same-provider private copy is not evidence of independent custody or an executed restore drill. There is no browser/API permission switch or restore executor in this phase.

## Release and separate action gates

Before source release: independent review of the exact successor and all required Linux workflows must pass at that exact head, including native PostgreSQL revision tests, normal server storage tests, and the inherited legacy recovery regressions. Synthetic fixtures prove code behavior, not production recoverability or provider availability.

Before installation or activation: confirm the live Render endpoint matches the authorized Supabase project; review/install 009 and 010 using an exact action-time approval and the current catalog/ACL gates; verify existing private bucket settings and backend key custody without exposing secrets; check the named tenant fits the limits and has no unresolved attachment bindings. The frozen 75 installation packet is dormant and must be reconciled with the eventual exact release before execution. Migration 011 is a new, separately reviewed and action-approved installation prerequisite. Missing admission RPCs/guards refuse the managed writer before storage writes; no fallback is used. The frozen 009/010 packet does not authorize or include 011.

Actual tenant data reads/copies, independent custody, a named revision/attachment-manifest recovery drill, cleanup/retention actions, source deployment, managed activation and a real Owner policy confirmation each require their separately bounded authorization. No production backup, file download, restore, installation, account/key/settings change, merge or deployment was performed to implement or test this draft.
