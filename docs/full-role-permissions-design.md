# Full role permissions: separate draft and implementation plan

Inspected main: `e949db64e744ebcb509623444c18a7c478e42880`, freshly confirmed October 7, 2026. The separate PM restriction draft is PR 74 at `56edd4f4f5e9a53885b056590c244b4029280f85`. Its exact-head CI and independent review pass. It is preserved as a narrower phase and does **not** satisfy the clarified request by itself.

The requested feature lets the owner change what Project Managers, field staff and office staff can view, create, edit and approve, and define a named custom role. This draft provides the full product matrix, route audit, rollout plan and a standalone policy model. It adds no runtime permission editor, server authorization hook, user assignment, production policy or grants. The model must not be enabled by importing it into the current route dispatcher.

## Role identities and scope

| Product label | Existing identity | Protected scope and limitations |
| --- | --- | --- |
| Account Owner | `owner` | Tenant ownership, account recovery, role administration and audit visibility remain fixed. Cannot be denied/deactivated/demoted by a role policy. Existing ownership changes stay separate. |
| Office team / Admin | `admin`; stored legacy `office` normalizes to `admin` | Company office access today. **Not** another owner: account creation/roles, tenant export/closure and billing remain owner-only. Time management requires existing individual `permissions.manageTime`. Pricing is currently inherent for Admin and cannot be generalized to field/custom roles. |
| Project Manager | `project_manager` | Assigned `projectIds` AND `assignedCrews`; existing five individual grants remain an additional ceiling. A role definition never expands assignments or grants. |
| Foreman | `foreman` (`/auth/me` displays field and retains `accessRole`) | Linked team member, crew and assigned-work scope; crew time view differs from field time view. Must not collapse this to generic office or treat UI display role as security identity. |
| Field team | `field` | Linked member, assigned/own work and eligible own time corrections. Approval stays office-only. Crew is a grouping, not a login role. |
| Named custom role | Proposed `customRoleId` on an existing non-owner account | Keep its protected `role` identity; custom definition has a fixed `baseRole` from Admin/PM/foreman/field and can only reduce that baseline. The custom label is not a new raw role string accepted by old handlers. A field custom role cannot become office/PM, gain assistant access or add project/crew scope. Assignment is a separate owner-confirmed action. |
| Platform / guest | Existing separate platform session or project guest token | Entirely outside tenant role policy; no custom inheritance. |

Custom definitions do not grant accounts any access simply by existing. Editing a built-in role or custom role definition, assigning a role to an account, changing an individual grant, changing project/crew membership and transferring ownership are distinct actions with separate impact previews. No self-assignment or self-escalation. A deleted/missing custom definition or missing whole policy fails closed for assigned users; preview must require reassignment before deletion. Retired IDs are permanently recorded and cannot be reused. Changing a custom baseline requires a new ID and separate owner-reviewed account assignments.

## Concrete control matrix

The proposed controls restrict that role's supported baseline; they never make an ineligible role eligible. Unsupported actions are visibly unavailable rather than checkboxes.

## Standalone prototype: implemented versus missing

`tools/role-policy-prototype.js` implements strict version-2 policy validation for all four editable built-in roles, 25 finite action IDs across schedule, dailies, time, notes, plans and photos, named restricted custom baselines, permanent retired-ID tracking, view prerequisites, tenant binding, invalid-policy fail-closed reduction and revision comparison. Owner decisions and ordinary built-in absent-policy baselines pass through exactly; a non-owner with a custom assignment fails closed when the policy is absent. Custom roles inherit built-in restrictions and existing account admissions. The prototype never replaces the account's security role or modifies stored grants/scopes.

Its inputs are **synthetic operation admissions**, not proof of access to a real route. It does not authenticate users, load project/member resources, check record state, create signed previews, persist policies/audits, assign custom roles, integrate UI, or revoke real requests. Those are runtime implementation work below. No app or server imports the model. The tests prove policy validation/reduction and immutability properties; they are not HTTP authorization coverage. Matrix rows outside the six modeled domains are design only and intentionally absent from the prototype allowlist.

## Integration plan and release gates

1. **Route coverage and default equivalence.** Enumerate every method+path including generic handlers, downloads, exports, workspace aggregates, side effects and private module early returns. The adjacent route audit names observed gaps. Build actual resource loaders/admission contracts; never use client-provided `role`, `capabilities`, `memberIds`, array index or a permissive generic dictionary as authority. Differential fixtures prove no-policy responses and mutations match existing defaults. Repair known IDOR/scope gaps separately with explicit tests; disclose any intentional default behavior correction.
2. **Current identity and immutable scope.** Assemble effective admission from the current tenant session/account at the shared `authenticateRequestAccount(req, db)` boundary being developed in the assistant draft, before assigning `req.auth`. Normalize legacy office/foreman identities once. Private notes, general manual routes, assistant preview/confirm/replay and storage access use that same actor. Scope resolves server-side project/member/report/workday references; AND tenant binding, PM project+crew membership and field/foreman identity on every linked object. A custom role is a secondary restriction profile, not a route-recognized role string.
3. **Operational V/C/E/A controls across built-ins.** Add explicit operation guards to every route in each domain plus corresponding workspace/aggregate projection. Separate approval/status transitions from edit, including daily status PATCH, change status PATCH, imports/proposals and time batch actions. Compound workday/time/report side effects require all relevant permissions. Pricing/payroll/billing/security stay separate immutable ceilings. Only advertise a control once every associated route, export, storage path and side effect is covered.
4. **Owner preview and confirmation protocol.** Extend the proven PR 74 pattern with a versioned document and authoritative revision/CAS. GET for owner/admin review; preview/apply only current active owner with permanent password, verified email if required and unlocked account. Signed five-minute preview binds tenant, session, owner, before revision, complete policy, reason, active users/roles/grants/scopes and custom assignments. Preview shows changed actions and affected users, including locks/outstanding work. Apply requires explicit confirmation, fresh auth and revalidation, saves policy+audit atomically, rejects stale/replayed/tampered preview, preserves owner recovery. Role assignment uses a separate preview/confirmation endpoint.
5. **Revocation during upload, execution and replicas.** Buffer governed uploads before authoritative tenant admission, then re-authenticate and resolve operations/scopes. Recheck immediately before mutation/side-effect/provider dispatch and before deferred response commit; abort/cancel when actor, policy or scope revision changes. Already committed operations remain recorded. Current queues and preview HMAC are process-local; multi-replica safety needs authoritative storage CAS/transaction admission and consistent shared preview binding, not cache/client flags. Do not claim distributed revocation until this exists. Stop new provider calls/notifications after revocation; cancel cancellable in-flight calls and reject their uncommitted result. Already delivered data/calls cannot be erased.
6. **Custom roles and UI.** Add owner-only create/edit/archive definitions, then separate owner-only assignment with active-user impact and no owner/baseline escalation. Require valid remaining owner, enforce maximum names/definitions and immutable baseline IDs, disallow destructive role deletion with active assignments. Company settings lets the owner select PM, Office/Admin, Foreman, Field or a named custom profile. Show actual V/C/E/A columns, immutable cells and project/crew scope text; no fake unsupported controls. Admin read-only. Derived effective actions refresh across tabs/account switches; server always uses current actor.
7. **Synthetic proof and independent review.** Per route/action × owner/admin/PM/foreman/field/custom × same/cross-tenant/project/crew/member, GET/POST/PATCH/DELETE/download/export; batch IDs and linked-object tampering; malicious unknown keys/prototype pollution; custom-owner/platform/field-assistant escalation; grant+cap implication cases; locked/approved record statuses and labor/rate invariants; stale/demoted/deactivated/expired sessions; preview/confirm/replay and ordinary/assistant uploads revoked while pending; role deletion/reassignment; CAS race and two-instance revocation. Full exact-head CI, fresh independent security review, isolated desktop/mobile UI QA. Draft only; deploy needs a separate concrete approval, and actual production role changes each need owner action-time preview/confirmation.

The runtime breadth is blocked by the documented legacy route gaps and distributed admission work. This is a reviewable design/model phase, not the completed requested editor. Other urgent branches and the assistant draft remain untouched. No SQL/migration, production account, provider call, permission change, merge or deploy was performed.
